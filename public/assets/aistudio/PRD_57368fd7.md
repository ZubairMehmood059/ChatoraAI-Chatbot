# Master Prompt: Build Chatora AI — A Premium AI Chatbot Web Application

## 1. Project Overview

Build a professional, modern, responsive AI chatbot web application named **Chatora AI**.

The application should provide a smooth conversational experience similar to modern AI chat products. Users should be able to send messages, receive intelligent AI-generated responses, maintain conversation history, and access useful productivity features through a polished interface.

**Primary objective:** Deliver a fully functional, secure, maintainable, and deployment-ready application, not just a frontend prototype.

## 2. Important Development Rules

- First inspect the existing project structure and understand the current implementation.
- Reuse the existing Python application and its architecture.
- Keep the frontend inside the existing `templates/` and `static/` directories.
- Do not unnecessarily rebuild or replace working code.
- Identify missing features, broken integrations, configuration problems, and security weaknesses before making changes.
- Implement the application end to end, including frontend, backend, AI integration, error handling, and deployment configuration.
- Do not fabricate functionality or display fake AI responses as if they came from a real model.
- Use clean, modular, readable Python code and sensible defaults.
- If an external API key is required, document how to configure it using environment variables.
- Do not hardcode API keys, credentials, or secrets.
- If the current project has no working AI provider, integrate a suitable provider through a clean, replaceable service layer.
- Make reasonable technical decisions independently and document any important limitations.

## 3. Recommended Technology Stack

Preserve the current stack wherever practical.

- **Backend:** Python with the existing Flask or FastAPI application.
- **Frontend:** HTML5, CSS3, JavaScript, and Jinja templates if Flask is used.
- **Styling:** Custom CSS with reusable design tokens and responsive layouts.
- **Database:** SQLite for simple local development, with a clean migration path to PostgreSQL.
- **AI integration:** A configurable LLM provider through a dedicated service module.
- **Configuration:** Environment variables loaded through `python-dotenv`.
- **Testing:** pytest for backend and API tests.
- **Deployment:** A production-ready WSGI or ASGI server appropriate to the existing framework.

Do not introduce React, Next.js, or a separate frontend build system unless the existing project genuinely requires it.

## 4. Premium UI/UX Design

Create a polished interface with a modern, premium visual identity.

### Main layout
- Professional sidebar containing the application logo, New Chat button, recent conversations, and settings.
- Main chat workspace with a welcoming empty state.
- Clean top navigation with model information and theme controls.
- Fixed or sticky message composer at the bottom of the chat.
- Responsive mobile layout with a collapsible sidebar.
- Clear loading indicators and smooth, subtle animations.

### Visual direction
- Premium dark and light themes.
- Refined typography, generous spacing, rounded corners, subtle shadows, and consistent alignment.
- A restrained color palette with accessible text contrast.
- Modern message bubbles or an unobtrusive assistant conversation layout.
- Attractive empty states, buttons, icons, and error messages.
- Smooth transitions without excessive animation.
- Support keyboard navigation and reduced-motion preferences.

Avoid generic template styling, excessive gradients, clutter, and unnecessary visual effects.

## 5. Core Chat Features

Implement the following features fully:

1. Send messages using a button or Enter key.
2. Receive real AI-generated responses.
3. Display user and assistant messages in chronological order.
4. Show a typing indicator while the assistant is responding.
5. Automatically scroll to the latest message when appropriate.
6. Disable duplicate submissions while a request is processing.
7. Display helpful errors when requests fail.
8. Provide a Stop Generating button where supported.
9. Provide a Regenerate Response action.
10. Add Copy Message functionality.
11. Support multiline input using Shift + Enter.
12. Preserve conversation context so the AI can answer follow-up questions.
13. Display timestamps or useful message metadata without cluttering the interface.
14. Include a New Chat action.
15. Support clearing or deleting conversations with confirmation.

## 6. Advanced Features

Implement these features in a modular way, prioritizing reliable functionality over a long list of incomplete features.

### A. Conversation Management
- Create multiple conversations.
- Automatically generate conversation titles from the first user message or through a title-generation service.
- Rename conversations.
- Delete conversations.
- Search conversation history.
- Persist conversations and messages in the database.
- Restore previous conversations after refreshing the page.
- Maintain correct conversation ownership if authentication is enabled.

### B. Intelligent AI Responses
- Use a real configurable AI model.
- Maintain context from previous messages in the current conversation.
- Support configurable model selection when the provider allows it.
- Add a system prompt defining the assistant's helpful, professional behavior.
- Handle provider errors, timeouts, rate limits, and unavailable models.
- Keep provider-specific logic separate from application routes.
- Never expose API keys to frontend JavaScript.
- Use streaming responses if supported reliably by the selected provider.

### C. Markdown and Code Support
- Render assistant responses with headings, lists, tables, links, and formatted text.
- Display programming code in syntax-highlighted code blocks.
- Add a Copy Code button.
- Render mathematical expressions if a suitable library is configured.
- Sanitize rendered Markdown and HTML to prevent cross-site scripting.
- Do not execute code submitted by users or returned by the model.

### D. File Attachments
- Allow users to upload supported text documents and PDFs.
- Extract readable content safely and make it available to the assistant.
- Validate file types, file sizes, and upload limits on the server.
- Store files outside publicly accessible static directories.
- Reject malformed files and handle extraction failures gracefully.
- Never claim to analyze a file unless its contents were actually processed.
- Keep the attachment feature modular so image understanding can be added through a compatible AI provider.

### E. Chat Export and Sharing
- Export conversations as TXT or Markdown.
- Add a print-friendly conversation view.
- Support conversation sharing only through an explicit, secure sharing mechanism.
- Use unpredictable share identifiers and allow share links to be revoked.
- Never expose private conversations through guessable public URLs.

### F. Personalization and Settings
- Dark and light mode with persistent preference.
- Adjustable response preferences where supported.
- Configurable model settings.
- Clear conversation history.
- Data deletion controls.
- Keyboard shortcuts and helpful tooltips.

### G. Optional User Accounts
If the existing application supports authentication, preserve and improve it. Otherwise, implement authentication only if it fits the project scope.

If accounts are included:
- Secure registration and login.
- Password hashing using an established, secure library.
- Session management and logout.
- User-specific conversation history.
- Server-side authorization checks for every protected resource.
- Account deletion and appropriate data cleanup.

Do not introduce authentication merely to make the project look advanced if it would compromise simplicity or reliability.

### H. Usage and Reliability
- Show a friendly error when an AI request fails.
- Add request timeouts and sensible retry behavior.
- Implement configurable rate limiting.
- Set reasonable limits on message length, upload size, and conversation history.
- Track basic operational metrics without logging sensitive message contents unnecessarily.
- Provide a simple health-check endpoint.
- Add request IDs or useful structured logs for debugging.

## 8. Backend and API Requirements

Create well-defined endpoints appropriate to the existing framework.

Suggested endpoints:

- `GET /` — render the chatbot interface.
- `POST /api/chat` — send a message and receive an AI response.
- `GET /api/conversations` — list the current user's conversations.
- `POST /api/conversations` — create a conversation.
- `GET /api/conversations/<id>` — retrieve a conversation.
- `PATCH /api/conversations/<id>` — rename or update a conversation.
- `DELETE /api/conversations/<id>` — delete a conversation.
- `GET /health` — report application health.

Requirements:
- Validate request payloads on the server.
- Use consistent JSON response formats.
- Return appropriate HTTP status codes.
- Handle malformed JSON, missing fields, invalid IDs, and database errors.
- Enforce conversation ownership wherever users or sessions are supported.
- Keep database operations separate from HTTP routing.
- Use database transactions where appropriate.
- Do not expose stack traces or secrets in production error responses.

Implement only the endpoints needed by the final application, but ensure every frontend action has a real backend implementation.

## 9. Security Requirements

Apply security best practices from the beginning.

- Store credentials and provider API keys in environment variables.
- Exclude `.env`, databases containing private data, uploaded files, and secrets from Git.
- Validate and sanitize all untrusted inputs.
- Protect against cross-site scripting and SQL injection.
- Configure secure session cookies and CSRF protection where applicable.
- Apply appropriate security headers.
- Restrict CORS to trusted origins if cross-origin access is needed.
- Add rate limiting to expensive endpoints.
- Enforce upload size and type limits.
- Avoid leaking private prompts, user data, credentials, or internal exceptions.
- Use HTTPS in production.
- Provide a clear privacy notice explaining relevant AI-provider data handling.
- Avoid storing sensitive conversation data in logs.
- Make debug mode configurable and disable it in production.

Do not assume that an AI-generated response is trustworthy HTML or safe to execute.

## 10. Database and Persistence

Use a suitable persistence layer for conversations and messages.

At minimum, define entities for:
- Conversations.
- Messages.
- Users, if authentication is enabled.
- Share links, if sharing is enabled.

Include timestamps, appropriate indexes, relationships, and deletion behavior.

Use migrations or a reproducible database initialization process. SQLite should work locally without requiring a separate database server. PostgreSQL should be supported through documented configuration if production deployment requires it.

Do not store all production conversations in an unmanaged JSON file.

## 14. Implementation Workflow

Follow this sequence:

**Phase 1 — Inspect:** Understand the repository, framework, existing files, and current functionality.

**Phase 2 — Plan:** Identify missing pieces, define the smallest reliable implementation plan, and note any breaking changes before editing.

**Phase 3 — Build:** Implement the complete chat flow, AI integration, persistence, responsive UI, and prioritized advanced features.

**Phase 4 — Secure:** Validate inputs, protect private data, configure sessions and rate limits, and review error handling.

**Phase 5 — Test:** Run the application and automated tests. Fix discovered issues.

**Phase 6 — Polish:** Refine the interface, accessibility, loading states, mobile layout, and failure states.

**Phase 7 — Deploy:** Prepare production configuration and verify the deployment if credentials and hosting access are available.

**Phase 8 — Report:** Summarize completed work, modified files, required environment variables, tests performed, known limitations, and exact run instructions.

The project is complete only when:

- The application starts using the documented command.
- The main page renders correctly.
- A user can submit a message and receive a genuine AI-generated response when the provider is configured.
- Missing API keys produce a helpful configuration error rather than a fake answer.
- Conversation history persists as designed.
